# ONNX Runtime 项目（SpacemiT 分支与厂商包）

AI 工作的 ONNX 侧。两个产物必须放在一起看：承载 SpacemiT 构建文件的公开分支，以及
板子上实际运行的闭源提供者包。

## 固定来源

| 字段 | 取值 |
|---|---|
| 上游 | `https://github.com/spacemit-com/onnxruntime.git` |
| ref | `upstream-1.24.2` |
| 提交 | `d76541ad26ca93d2d52e5d2db2aacaff862df5cf` |
| 许可证 | MIT |
| 检出 | `src/onnxruntime` |
| 厂商包 | `spacemit-ort.riscv64.2.0.6.tar.gz`，包提交 `5a5b5914` |

提供者本身没有以源码形式发布：分支里只有工具链文件与一个提供者测试工具，发布包则
提供 `libonnxruntime.so.1.24.2+spacemit.a1` 与已 strip 的
`libspacemit_ep.so.2.0.6`。因此 `sources.lock.yaml` 同时登记分支的文件摘要与密封
包身份，以及我们被允许使用的公开入口。

  `OPTIMISATION2-20260921.md` 第 3 节把同一套方法做成一进一出的筛选器
  （`tools/board-coverage-census.sh` + `tools/ort-provider-census.py`）：十个模型里七个完全没有 CPU
  回退；`pp_liteseg` 有 25.5 % 的帧时间落在 CPU EP 上（13 次节点执行，与独立的双跑估计 26.8 % 吻合）；

  `VLM-SERVICE-SHAPE-20260921.md` 把同一个问题问到 VLM 服务上，答案正好相反：并发请求共享同一遍权重
  读取，4 路并发解码的聚合吞吐是单路的 **2.91 倍**、单流只掉 19 %；带图像时只有 1.77 倍，因为视觉
  阶段每帧都重新编码并与解码争抢同样那 8 个核；编码器宽度（模型 `config.json` 里的一行）在该负载下
  值 14 % 的聚合吞吐。
  该文第 5 节把"让视觉阶段离开关键路径"的三条路都用数字否掉：X100 跑同一个编码器慢 30 倍（4.56 s 对
  152 ms）；把到达错峰只重新分配延迟、不提升吞吐；把编码器收窄反而让解码更差。`SESSION-OPTIONS-20260921.md`
  则在三个模型上扫会话级旋钮：厂商的图优化默认档就是对的（99 档在 ±2.5 % 内），`-o 0` 在回退重的分割
  模型上贵 18.2 %、并行执行器贵 9.8 %，而内存策略那一族（arena、pattern、spinning、env allocators）
  在 ±1 % 内全平。
  第 7 节补上 VLM 类的第二个模型（厂商 Qwen3.5-0.8B 包）：第 7 轮每条结论的**方向**都复现、幅度都更小
  （文本解码 2.91 倍 → 1.88 倍，图像路径 1.77 倍 → 1.34 倍，编码器宽度值 52.6 ms 首 token 延迟而非
  87.3 ms）；而该模型官方那一行**对不上任何候选口径**——我们单测的编码器比官方快 25-29 %，首 token
  延迟却慢 22-47 %——等于在第二个模型上再次确认验收规则 R10。同时暴露两个操作陷阱：Qwen3.5 家族必须
  带 `--reasoning-budget 0 --reasoning off`，否则回答为空而 token 照计；服务端自报的 `image prefill`
  在两种模型上都对编码器宽度不敏感。
  第 8 节用现有仪器把那段"图像阶段"拆开了：让**服务进程内部**的 EP 自己吐 trace（每次请求只有一次
  ~195 ms 的编码器执行），再用纯文本对照给 prompt token 定价（6.6-7.1 ms/token），最后用包里 224/384
  两个分辨率拟合出 `阶段 ≈ 编码器 + 4.7 ms × 图像 token 数`（384²：162 token/969 ms；224²：67 token/
  367 ms）。也就是说**每帧图像成本由图像 token 数决定，而不是编码器**——编码器只占那一段的 20 %，
  因此分辨率变体才是杠杆，编码器线程数对它几乎无效。
  第 9 节把**图像当作受控变量固定**，在唯一可作同类比较的轴上超越官方那一行：384² 的视觉编码器相对它
  **-30.7 %**（4 核列）与 **-24.7 %**（8 核列），且厂商文档里那条 dense-accuracy 设置实测为中性。九个
  图像无关的运行时配置（flash attention、batch 线程、micro-batch、mmap、KV 量化及组合）全部在 ±0.8 %
  内或更差——KV `q8_0` 让图像路径贵 20 %；而厂商自己那条核数轴已达最优：4 路负载下 LLM 8 + 视觉 8 是
  15.40 t/s，把语言模型砍到 4 核只有 9.71/9.87 t/s。低分辨率变体按"实测但出界"记录（那是换图像而不是
  优化）：224² 每帧可省约 600 ms，而九问客观筛查在 224/384/768 上都是 12/18、**错在同一批题**。
  第 10 节定位了我们服务端预填与该模型官方**语言行**之间那 25 % 的去向：媒体后端只占 1.3 %（用不带
  媒体参数起的服务对照测得），**服务形态**占 13 %（同权重下厂商自己的 `llama-bench` 是 160.73-162.07
  t/s，服务端是 141.35 t/s），而官方那一行又比厂商自己的工具高 12.7-13.7 %——与之前 LLM 各行的
  "约 10% 乐观"一致，现在预填行也量到了。三者都不是本板运行时旋钮能改的；可复现的领先在编码器
  （8 核 **-24.7 %**）。
  `YOLO-OPTIMISATION-20260921.md` 汇总 YOLO 家族全图，含此前几轮没做的三项测量：**EP 自身选项**（六款
  检测器都是"8 线程单流"最优；绑核只在 4 线程上值 +3.1 %，而 4 线程本身慢 49 %）、**八个核按线程×流
  分解**（拆流损失 8-53 % 聚合吞吐）、以及**X100 当协处理器**（`yolov8n` 892.8 ms 对 AI 核 9.17 ms，
  97 倍）。持续负载无衰减（三分钟稳定 105.4 inf/s）。未解问题是拟合出的**每帧 4.2 ms 不随核数扩展**
  （占帧时间 45 %），运行时自报的 `/dev/tcm_sync_mem` 回退是候选之一——已定价，未验证。
  该文第 7 节回答更硬的问题——**硬件是否已达极限**——答案是**否**：对照厂商自己的 `cpufp` 峰值（INT8 矩阵
  单元每核 511.53 GOPS、4 核 2.046 TOPS），一次 YOLOv8n 推理实际只取出 **912 GOPS = 八核峰值的 24.8 %**
  （按板卡实际运行的 1.8 GHz 折算；AI 核已在其最高频，X100 只跑到 2.0/2.15 GHz）。缺口分解为**每核内核
  效率约 43 %** 与**并行扩展 60 %**；且该负载是**算力受限**而非带宽受限（权重流量约 3.1 GB/s，屋顶
  26 GiB/s）。配置轴已探尽，基础算力并没有——缺的那 4 倍在闭源 provider 内部。
  按 K3 A100 的 INT8 稠密规格（约 15 TOPS，由使用方给出；本地文档只有 K1 实测的 511.53 GOPS/核），同一次
  推理的达成率是 **6.1 %**，而 **provider 自己的 per-op trace** 说明了原因：**执行时间里有一半根本不是
  矩阵运算**（激活/softmax 24.7 %、Concat 11.3 %、Transpose 5.4 %、量化 3.5 %、形状搬运 2.8 %），而矩阵
  那一半只跑到峰值的约 12 %。两个屋顶都没被打满（算力 6-25 %、内存 11 %），因此该节也**收回了我先前
  "compute-bound" 的措辞**——真正的限制是该 provider 执行这张图的方式。
  第 8 节把同样的画像铺到整个家族（每模型一份 provider trace）：**每个 YOLO 模型都有 40-50 % 的执行时间不是
  INT8 矩阵运算**（`yolov8s` 40.2 %，其余 49.3-50.2 %），且**没有任何单个算子占比超过约 6 %**——`yolov8n`
  里最贵的单算子是检测头的 Softmax（占线程时间 5.6 %），而每帧要执行 512 次卷积、544 次激活、136 次 Concat、
  48 次 Transpose。每个架构还有自己的"非矩阵签名"（分割头 15 % 在 Transpose、`yolo12n` 31 % 在激活、DFL 头
  约 12 % 在 Softmax/Concat/Sigmoid、no-DFL 头 13 % 在 ReduceSum 与两次 Transpose）。为记录而定价（两者都出
  契约）：去掉整个非矩阵一半约值 2 倍，仅去掉分割头的 Transpose 最多值该模型 15 %。
  `MODEL-ALTERNATIVES-20260922.md` 开启**由你指定的"模型替代"轨道**（与被冻结模型的优化轨道分开）：
  记录两处实测弱势（`pp_liteseg` 25.5 % 帧时间落在 CPU EP、`yolo26n` 8.2 %），把厂商自己的 42 个模型族
  映射到常见视觉领域，给出**已实测为 EP 完整覆盖**的同域替代（`yolov8n-seg` 12.85 ms 对官方 12.75；
  `yolov8n/s`、`yolo12n`），并按优先级列出空白领域与经 HEAD 核对的清单：pose 3.80 MB、depth 10.46 MB、
  OCR 检测+识别 2.03 MB、人脸识别 1.07 MB——前四个候选合计仅 **16.3 MB**，所以障碍不是获取而是决策。
  另外记录一处证据完整性问题：归档中名为 `rfdetr-nano.fp16.onnx` 的文件其实是 434 字节的归档错误页，
  不是模型。
  `OPERATOR-CONVERTER-20260922.md` 回答下一个问题——**能否重写图，让 provider 全盘认领**——依据是本项目
  实测出的三份回退清单：深度模型 18.4 %（`Resize` 6.34 ms、`Cast` 2.14、`Pow` 2.00、`Exp` 0.11，**除
  `Exp` 外全部在 provider 支持清单里**，说明这些是"能力检查"失败而非算子缺失）、`pp_liteseg` 25.5 %、
  `yolo26n` 8.2 %。厂商自己的 `onnxslim` 在深度模型上跑完**什么都没变**（算子数与那 15 次 CPU 节点执行
  完全一致），所以"能力驱动"的转换器是真空白而不是重复造轮子。文档给出按实测收益排序的规则库、必须先过
  的数值门，并把 `yolo26n-depth` 定为第一目标——关掉它的回退可把该帧从 67.62 ms 推向约 55 ms。
  该文第 5 节是按你的要求写进项目的**转换逻辑要求：先查询、后动手**——证据分三级（文档约束、跨模型"被认领/
  被拒"对照、厂商例程代码），探针只允许用来**确认**已推导出的规则、不得用来"试错捞鱼"；每条规则必须记录
  证据、数值门结果、再普查结果与状态（accepted/rejected/needs more query）。证据登记册的结论：`Resize`
  的 `nearest+asymmetric` 处处被认领；`linear+half_pixel` **在 QDQ 图内**被认领（`pp_liteseg` 7/7，且能在
  provider 自己的子图 dump 里核到），但作为**独立 fp32/fp16 节点被拒**；而最自然的那种 Gather 改写会让
  provider **段错误**（各个基本算子单测却都通过）——这本身是一条健壮性问题。四条候选规则被证据否决、没有
  一条被当成猜测发出去；活下来的那条查询线（Q/D/Q 包裹探针）及其 6.34 ms 价签都已写明。
  探针给出的答案更好（第 6 节）：真正的判别项是**上下文**而不是算子——单独的 `half_pixel+linear` Resize
  100 % 落在 CPU EP，而**紧跟一个 Conv 的同一个节点**被完整认领、零 CPU 节点。这一下解释了全部观察：
  `pp_liteseg` 的 7 个 linear Resize 生在大型被认领区域里，深度模型的则被不支持的 `Exp` 切成碎片。
  于是去掉那个 `Exp`（`Exp → Pow(E,x)`，数值门 0.03 fp16 ulp）——机制预测被完全证实：CPU 节点执行
  15 → 8、占比 18.4 % → 8.0 %——**而该帧慢了 16 %**（64.52/64.59 ms 对 74.93/74.83 ms），故按净效果
  否决该规则："CPU 节点变少"并不等于"更快"。下一条查询已命名并带价签：为什么重新连通后的区域比它替换掉的
  CPU 碎片贵约 16 ms——背后有一个 Conv+一个 Resize 的复现探针。
  `VENDOR-QUERY-20260922.md`（中文，可直接发给厂商）把这条问题写成支持报告，含三项可复现问题：受支持
  算子**孤立时被拒、紧邻卷积时被认领**；重新连通后的区域在 provider 上**比它替换的 CPU 碎片慢 16 %**；
  以及 Gather 组合让 provider **段错误**（而非拒绝）。每项都带探针、数字与明确提问；最小复现随证据目录
  （`model-alternatives/converter-r1/vendor-query-probes/`）一并保存。
  替代品文档第 8 节完成四个已批准候选的第一轮验收：`yolov8n-pose` **EP 完整覆盖、11.195 ms 对官方
  11.16 ms——官方视觉行第三次被复现到 0.3 % 内**；OCR 检测（35.99 ms）、识别（2.358 ms）与人脸嵌入
  （3.137 ms）均 EP 完整覆盖并建立新基线，其中识别模型尤其值得记：它是**厂商出货的动态量化模型，被
  provider 完整认领**——而我们自己用 `xslim` 产出的 dynq 曾被拒，差别在于是谁做的产物。TCM 在 400 次
  姿态推理长跑中采样为 `available_blocks=0/8`。深度候选按"带已知缺陷"接受（64.84 ms，18.4 % 帧时间在
  CPU 侧，四条改写路线试过、无一留作待办）。
  `src/onnxruntime` 未做任何修改。
