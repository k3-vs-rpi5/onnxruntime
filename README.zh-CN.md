# ONNX Runtime 项目（SpacemiT 分支与厂商包）

AI 工作的 ONNX 侧。两个产物必须放在一起看：承载 SpacemiT 构建文件的公开分支，以及
板子上实际运行的闭源提供者包。

## 固定来源

| 字段 | 取值 |
|---|---|
| 上游 | `https://github.com/spacemit-com/onnxruntime.git` |
| ref | `upstream-1.24.2` |
| 提交 | `d76541ad26ca93d2d52e5d2db2aacaff862df5cf` |
| 许可证 | MIT |
| 检出 | `src/onnxruntime` |
| 厂商包 | `spacemit-ort.riscv64.2.0.6.tar.gz`，包提交 `5a5b5914` |

提供者本身没有以源码形式发布：分支里只有工具链文件与一个提供者测试工具，发布包则
提供 `libonnxruntime.so.1.24.2+spacemit.a1` 与已 strip 的
`libspacemit_ep.so.2.0.6`。因此 `sources.lock.yaml` 同时登记分支的文件摘要与密封
包身份，以及我们被允许使用的公开入口。

  100 % 落在 CPU EP，而**紧跟一个 Conv 的同一个节点**被完整认领、零 CPU 节点。这一下解释了全部观察：
  `pp_liteseg` 的 7 个 linear Resize 生在大型被认领区域里，深度模型的则被不支持的 `Exp` 切成碎片。

  38.33 ms 对重叠 38.42 ms，所以**这两级应当在同样 8 个核上串行**，而不是各占一半。
  转换器文档第 5.0、7 节随后收紧方法论并把它用到回退最大的两个模型上。**交战规则**（由本项目自己的两次
  失误换来）：形式由**被生成算子**的 opset 决定（`ReduceSum` 自 opset 13 起 axes 为输入；`ReduceL2` 到
  opset 18 才改）；"等值 / 被认领 / 更快"是三件独立的事、要三个仪器；**先归约再归因**；反常是观测不是结论。
  `yoloe` 的三个 `Einsum`（58.88 ms，占帧 37.4 %）被精确降级为 `Reshape/MatMul/Reshape`（1.79e-07），
  回退如期消失（CPU 节点 12→7、占比 37.9 %→0.1 %）——**而整帧 157.55 → 544.35 ms**，因为 provider 的
  `MatMul` 路径耗约 405 ms/帧，而 CPU EP 上等价算术只要 58.9 ms：**慢 6.9 倍、等效 1.7 GOPS**。
  `superpoint` 那 1 个 `ReduceL2`（0.434 ms）被降级为位级一致的 `Sqrt(ReduceSum(x*x))`，而 provider
  **在会话初始化成功后、首次推理时段错误**，基本算子、形状、dtype 上下文、归约轴均被探针排除——记
  **blocked-unexplained**，复现与"旁边全部通过的探针"一起交厂商。
  第 7.3 节用**查询而非代码**关闭第三个带缺陷候选：`mobilesam_decoder` 的 `Shape`×36 / `Expand` /
  `Not` / `OneHot` 看起来是"可折叠的形状管道"，但把节点与"形状推断真能证明的形状"对齐后是 **36 个里 0 个
  静态**——该模型是**可提示解码器**，`point_coords [1, num_points, 2]` 使那一维是真正的运行时变量。假设在
  任何产物生成之前就被否掉；剩下两条精确规则（`Not → Equal(x,false)`、`OneHot → Gather`）动不了摊在 270 个
  节点上的 8.59 ms；而该候选可优化的形态是"静态提示解码器"＝改模型，按 20.3 % 帧时间记录、不留待办。
  第 8 节是转换器**第一条被接受的规则**，且是"先立预期"的受控实验：`Not(x) → Equal(x,false)` 位级一致、恰好把
  三个节点（`/Not`、`/Cast`、`/Mul_2`）从 CPU EP 挪走（无新节点进入），`mobilesam_decoder` 从
  28.94/28.74 ms 降到 28.38/28.43 ms（约 1.8 %、约 0.5 ms）。有意思的是它**不是**什么：区域并未连通
  （270 次节点执行里仍有 267 次在 CPU EP），收益来自"边界挪了三个节点"——这**证伪**了"一个不支持算子会切断
  整个区域"（至少在这张图上），同时确认了更小的那条机制。`OneHot → Gather` 同样精确（把 values 补零到
  `depth=5`），但它自身只值 0.06 ms：已定价、未实现，且明确**不基于已被证伪过一次的假设**去写它。
  第 11 节把 10.1 节点名的那个产物做出来了——`tools/ort-two-session-pipeline.cpp`：**同进程双会话**，
  EP 按厂商自己媒体引擎的方式加载（Python 里写 `providers=[...]` 会**静默回退到 CPU EP**，这样就会
  "测了 CPU 却以为测了 AI 核"）。两条发现改写了部署规则：AI 核是**按会话分配**的（8+8 被直接拒绝：
  "required 8, available 0"，且 `SPACEMIT_EP_USE_GLOBAL_INTRA_THREAD` 不能解除该限制），所以两个会话
  必须 4+4 分核；而 4+4 重叠给出 **43.10 fps 对串行 27.76（1.55 倍）**、单级仅 +9.0 %/+5.5 %，并且比
  "两进程各 8 核轮流跑"还快 **5.7 %**——因此原先的"单进程、两级串行"规则更新为**单进程、双会话、4+4 分核、
  两级重叠**。运行中采样的 TCM 表显示八块被两组线程各占四块。
  第 11.1 节进一步**把分核搜索出来而不是假设**：SAM 这一对的两级缩放差异极大（编码器 8→4 线程损失 59 %，
  解码器仅 8 %），4+4 得 15.20 fps、5+3 得 16.64、**6+2 得 18.94**、7+1 反而 16.32——最优点落在"编码器仍是
  瓶颈"的边界上，再多给一核就把瓶颈交给解码器、代价 14 %。相对已知最好的非流水线形态（两进程各 8 核轮流，
  14.43 fps）**+31 %**；相对同进程两级串行 **+81 %**。
  第 12 节把这套方法用到 VLM 上，并按你的要求**每一行都对着官方基准**：编码器曲线在官方给出数字的两个宽度上都**领先**
  ——我们 4 核 243.08 ms 对官方 256.47（-5.2 %）、8 核 150.02 对 164.50（-8.8 %）；解码器无官方数字，已注明。
  单流组合最优点是 (2,6)、410.1 ms/帧，比"8+8 串行"快 27 %——**而真实服务否掉了它**：四个 slot 下"编码器 2 +
  文本 6"只有 32.22 t/s，而"编码器 8 + 文本 8"是 47.88 t/s；原因是 llama-server 重叠的是**请求**，而 ORT 流水线
  重叠的是**阶段**。所以第 11 节的方法是**单流**工具，VLM 的部署规则保持"一个服务、4 个 slot、编码器 8、文本 8"，
  被否掉的预测原样留在表里当反例。
  第 13、14 节是你要求的**调研轮 + 验证轮**，两侧都对着厂商自己的文档：他们的 12 路视觉应用（`yolov8n`
  **总计 134.29 FPS**、"多会话轮转"）与 ASR 的分配规则（`-np 4`、编码器绑核 `8;9`、解码器在 `10-15`）。
  小视觉模型侧的验证**首次让本项目超过官方发布总量**：一个进程内 8 个 1 线程会话跑 `yolov8n` 达
  **151.50 inf/s，+12.8 %**（TCM 8/8 块、8 个不同线程 id）；单会话 8 线程只有 106.27/s（-20.9 %），
  4×2 与官方相差 2 % 内。这也**给第 5 轮的"并发持平"划了范围**：那只对 `-c` 并发运行与两进程拆分成立，
  对**同进程多会话**不成立。VLM 侧则直接验证了厂商 ASR 的分配规则——**不外推**（绑核 32.06 t/s 对实测最优
  47.88），因为 ASR 是"流式编码器 + 离线识别器"并行，而 VLM 是每个 slot 各自"编码→解码"。
  `NEXT-ROUND-ANALYSIS-20260922.md` 是你要的这一轮——不跑测量，只做"后续该做什么"的分析（本轮**零板卡时间**）：

  LLM 解码行降级为上下文），再列出**已经关闭、不要重开**的问题清单，然后把"只差一次测量"的若干问题逐个定价

  `AI-CLUSTER-PEAK-20260922.md` 执行了该计划的第一项。用**纯矩阵 QDQ 探针**（厂商自家模型使用的形态
