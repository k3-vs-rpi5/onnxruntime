# ONNX Runtime on K3: second measurement round - precision gate, per-frame cost, interference

Follows `BASELINE-20260921.md` (latency/thread/TCM/coverage/operator/VLM tables). Same instruments
(the sealed 2.0.6 `onnxruntime_perf_test` with the vendor's option set; the board's packaged
`llama-server --media-backend smt` for VLM). Raw data: `/root/k3-evidence/onnxruntime/
baseline-20260921/` (`gate-resnet50-*`, `board-vlm/vlm-frame*`, `bw-*.log` on the board, plus the
round-one trees).

## 1. The fp16-epilogue knob is inert for QDQ models (D3, negative result with a working gate)

`SPACEMIT_EP_DISABLE_FLOAT16_EPILOGUE=1` is documented as disabling "FP16 scaling in quantized
Conv/Gemm". Measured on the int8 zoo models at 8 AI cores:

| model | epilogue on | epilogue off | delta |
|---|---|---|---|
| vit_b_16 int8 | 23.384 ms avg (first 944 ms) | 23.370 ms (first 946 ms) | -0.06 % |
| resnet50 int8 | 5.476 ms (first 108 ms) | 5.494 ms (first 107 ms) | +0.3 % |

and the numeric gate says the same thing: with `SPACEMIT_EP_DUMP_TENSORS` capturing **60 intermediate
tensors** of resnet50 in both settings, **all 60 are bit-identical** (pure-Python `.npy` comparison,
`<i1` int8 and float tensors alike). So for statically-quantised QDQ graphs the knob changes neither
time nor numbers; it must belong to the vendor's dynamic-quantisation path (see the
`SPACEMIT_EP_DENSE_ACCURACY_LEVEL` documentation: 0 = dynamic quantisation, 1 = fp16, 2+ = fp32, for
"Online MatMul in dynamic quantization models").

Two things this round buys beyond the negative result: the **numeric gate works and is cheap**
(dump + compare, exact equality when nothing should change - the same discipline the kernel work
uses), and the accuracy levers for *this* model family are the ones the zoo already quantises with
(`xslim`, the vendor's PTQ tool, is the documented path for an int8 encoder; not attempted here).

## 2. Cold start and first inference (D6, from the round-one logs)

Per model at 8 AI cores, same instrument:

| model | session create | first inference | steady state | first / steady |
|---|---|---|---|---|
| resnet18 int8 | 0.086 s | 73 ms | 2.08 ms | 35x |
| resnet50 int8 | 0.235 s | 109 ms | 5.50 ms | 20x |
| yolov8n int8 | 0.527 s | 62 ms | 9.58 ms | 6.5x |
| yolov8n-seg int8 | 0.631 s | 80 ms | 12.88 ms | 6.2x |
| yolov8s int8 | 0.535 s | 101 ms | 16.60 ms | 6.1x |
| vit_b_16 int8 | 0.548 s | 961 ms | 23.56 ms | 41x |
| vit_b_16 fp16 | 0.280 s | 474 ms | 51.14 ms | 9.3x |
| fastvlm vision fp16 | 0.557 s | 783 ms | 150.89 ms | 5.2x |

Consequences for deployment: a per-frame service that creates a session per request pays 0.09-0.63 s
plus a first inference that is 5-41x the steady state; a warm session pays only the steady state. Any
measurement or product claim has to say which of the two it is, and a robotics loop must hold the
session open (the same "durable pool" lesson the LLM work paid for, one level up).

## 3. VLM per-new-frame cost (D6)

Three visually distinct 64x64 frames (red/blue diagonal, green square on black, blue/white rings) plus
a repeat of the first, one server, greedy, `-t 8`, encoder at its default 4 threads:

| request | frame | prompt tokens | prompt eval | decode | total | answer |
|---|---|---|---|---|---|---|
| 1 | a | 90 | 354.75 t/s | 48.37 t/s | - (first request, session warm) | "A simple, solid red background with a diagonal blue stripe." |
| 2 | b (new) | 69 | 378.63 t/s | 46.99 t/s | - | "A green square with a black square in the center." |
| 3 | c (new) | 69 | 370.00 t/s | 46.54 t/s | **680.72 ms** / 92 tokens | "The image depicts a series of concentric circles with alternating blue and white..." |
| 4 | a again (cached) | 1 | 46.29 t/s (21.60 ms) | 49.27 t/s | **285.44 ms** / 14 tokens | identical to request 1 |

So **every new frame re-runs the encoder** (inside the prompt-eval window, ~186-250 ms at 4 threads),
and a cached frame skips it: 681 ms against 285 ms end to end on this model. For a 30 Hz perception
loop the encoder is therefore paid 30 times a second unless the service is engineered around it; for
a *language-conditioned* policy loop the frame rate is set by the pair (encoder + decode), not by
decode alone. This is the measurement the deep analysis asked for as D6.

## 4. X100 read load against AI-cluster stages (D7)

Load generator: the campaign's `bw_read` (X100 threads on cpu0-7, 512 MiB buffer, 9 s), the same tool
the earlier interference ladder used. Model latency from `onnxruntime_perf_test` (10 repeats for the
ViT, 5 for the encoder):

| X100 load | ViT-B int8 @8 AI cores | fastvlm encoder fp16 @4 AI cores |
|---|---|---|
| none | 23.35 ms | 241.86 ms |
| 1 thread, 6.77 GiB/s | 24.38 ms (+4.4 %) | 252.73 ms (+4.5 %) |
| 4 threads, 12.60 GiB/s | 27.01 ms (+15.7 %) | 273.74 ms (+13.2 %) |
| 8 threads, 15.18 GiB/s | 29.20 ms (+25.1 %) | 274.05 ms (+13.3 %) |

Same order as the LLM campaign's ladder (an X100 read at 6.8 GB/s cost the 30B decode ~14 %), which
means the two clusters share one DRAM roof in practice for this stack too. Two details matter for
placement: the penalty is **sub-linear in the load** (6.8 -> 15.2 GiB/s buys 4 % -> 25 % on the ViT),
and the int8 ViT is more sensitive than the fp16 encoder at the same 4-thread load (25 % against 13 %),
consistent with the int8 path doing more bytes per FLOP.

## 5. Where the plan stands after two rounds

| direction | state |
|---|---|
| D1 EP thread/TCM census | **answered** (round 1): N intra threads -> N+1 process threads, N TCM blocks, one AI core each |
| D2 subgraph coverage | **answered** (round 1): one subgraph per model, Attention/LayerNorm/Gelu included |
| D3 precision | **half answered**: the epilogue knob is inert for QDQ; int8 vs fp16 is 2.17x on ViT; the int8-*encoder* needs `xslim` (documented PTQ tool) - not attempted |
| D6 fixed costs | **answered** (this round): session/first-inference table, and the VLM per-new-frame cost |
| D7 two-cluster placement | **answered** (this round): the interference ladder above |
| D4 thread split | superseded (round 1): the engines serialise on the 8-block TCM table |
| D5 plugin ops | not needed for the measured architectures (round 1 coverage result) |
| D8 real-time methodology | open; the harness records P50/P90/P99 already, a control-loop definition of done is a human decision |

Next candidates, in value order: (1) an int8 vision encoder via `xslim` with the tensor gate - the
2.17x on ViT says what is at stake for the VLM's 35 % encoder share; (2) a sustained-frame test for a
specific robotics loop (fixed cadence, P99 latency, thermal drift over minutes); (3) `DENSE_ACCURACY_LEVEL`
sweeps on a dynamically quantised encoder (the ASR packages ship `dynq` encoders and are the family the
knob actually targets).
