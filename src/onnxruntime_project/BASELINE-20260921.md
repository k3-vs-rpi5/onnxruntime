# ONNX Runtime on K3: data baseline (2026-09-21)

First measurement round of the project, run to establish the numbers everything else will be
compared against. Instrument: the sealed release package's own `onnxruntime_perf_test`, with the
exact option set the vendor's published model-zoo tables used
(`-e spacemit -r 10 -x 1 -S 1 -s -c 1 -i "SPACEMIT_EP_INTRA_THREAD_NUM|N" -I`), so local numbers are
comparable with `modelzoo.md` rather than with a private harness. Raw logs, traces and dumps:
`/root/k3-evidence/onnxruntime/baseline-20260921/` (board-logs/, board-vlm/).

Reading: the environment and the instrument reproduce the vendor's table to within a couple of
percent on seven of eight models. The fp16 ViT at 8 cores is the one outlier (+4.9 %); the int8 twins
match, so it is a precision-path effect, not a board or instrument difference.

question "what if the provider is not used":

| model | 4 X100 cores | 8 X100 cores | provider 8 AI cores | provider speed-up |
|---|---|---|---|---|
| resnet50 int8 | 366.34 ms | 244.84 ms | 5.50 ms | 45x |

| yolov8n int8 | 1396.94 ms | 887.88 ms | 9.58 ms | 93x |

The quantised models are the worst case for the CPU EP (the QDQ graphs dequantise into fp32 paths),

## 2. Thread and TCM behaviour (D1, answered)

Sampled while a provider run was in flight (`logs`: `ev-*.txt` on the host copy, `board-logs/`):

| `SPACEMIT_EP_INTRA_THREAD_NUM` | process threads | threads pinned to AI cores | TCM blocks held |
|---|---|---|---|
| 1 | 2 (main + 1) | 1 (cpu8) | 1 / 8 |
| 4 | 5 (main + 4) | 4 (cpu8-11) | 4 / 8 |
| 8 | 9 (main + 8) | 8 (cpu8-15) | 8 / 8 |

* The EP creates **exactly N compute threads**, each pinned to one AI core and each holding one TCM
  block. The documentation's "`2 x intra_thread_num` compute threads are launched" does **not** match
  what the 2.0.6 package does in this configuration.
* The main thread stays on the X100 (cpus_allowed_list `0-7`); the compute threads show ~88 % "CPU" in
  the Linux-side view - the contract's warning that Linux instruments under-count AI-core work.
* In `onnxruntime_perf_test` the blocks stay claimed for the whole run; in `llama-server`'s smt media
  backend they are taken per stage and released afterwards (idle server = 8/8 free).

## 3. Subgraph coverage (D2, answered)

`SPACEMIT_EP_DUMP_SUBGRAPHS=1` (a flag, not a path; dumps land in the working directory with the fixed
`SpaceMITExecutionProvider_SpineSubgraph_` prefix - the documentation's wording matters, a path value
silently disables the dump):

| model | subgraphs | op types inside the provider's subgraph |
|---|---|---|
| vit_b_16 int8 | **1** | Conv, MatMul, Gemm, **Attention**, **LayerNormalization**, Gelu, QuantizeLinear, DequantizeLinear, Add, Mul, Concat, Gather, Reshape, Split, Transpose |
| yolov8n int8 | **1** | Conv, MaxPool, Resize, Slice, Concat, Add, Sub, Mul, Div, Sigmoid, Softmax, Transpose, Reshape, QuantizeLinear, DequantizeLinear |
| fastvlm vision fp16 | **1** | Conv, Gemm, MatMul, AveragePool, ReduceMean, **LayerNormalization**, Gelu, Softmax, Sigmoid, Add, Mul, Clip, Cast, Reshape, Squeeze, Transpose |

Every model ends in a single provider subgraph, and the transformer ops the accelerated-operator page
does not list (Attention, LayerNormalization, Gelu) are inside it. The plugin-API concern from
`DEEP-ANALYSIS.md` D2/D5 is therefore *not* a coverage gap for these three architectures - what the
provider does with those nodes internally (its own kernels vs an internal fallback) is a separate
question, and the profile traces below are where it would show.

Consequence for the optimisation agenda: a CNN has a few operators worth attacking; a ViT has none -
its time is spread over ~300 small nodes, so only *precision* and *per-node overhead* move it.

## 5. Precision baseline

ViT-B/16, same input, same thread counts: **int8 23.56 ms against fp16 51.14 ms at 8 cores (2.17x)**;
at one core 99.49 against 140.70 ms (1.41x). The vendor's VLM package ships an **fp16** encoder
(`fastvlm_vision.f16.onnx`), so the VLM path currently pays the fp16 price while the classification
path shows what an int8 encoder would buy. This is D3 and it now has both ends measured.

## 6. VLM end to end (fastvlm-0.5B, vendor llama-server with `--media-backend smt`)

The board's packaged `llama-server` runs the documented shape: vision encoder through this ONNX EP
(`[SMT][vision] Spacemit EP enabled (SPACEMIT_EP_INTER_THREAD_NUM=1, SPACEMIT_EP_INTRA_THREAD_NUM=4)`,
a separate media-worker thread), LLM through llama.cpp. One 64x64 PNG, greedy, `-t 8 -ctk f16 -ctv f16
-c 1024`:

| stage | first request | second request (same image) |
|---|---|---|
| image encode | inside the 249.34 ms prompt-eval window (the standalone encoder measures 241.52 ms at 4 threads) | - (embedding cached: `prompt_n=1`) |
| prompt eval | 249.34 ms / 95 tokens (381.00 t/s) | 46.49 t/s equivalent, 1 token |
| decode | 444.72 ms / 20 tokens (22.24 ms/token, 44.97 t/s) | 44.37 t/s |
| total | **694.06 ms** | - |
| answer | "The image is a simple, two-color design featuring a diagonal blue stripe on a red background." | identical |

Cross-check with the vendor's VLM table: moving the vision side from 4 to 8 cores saves 92 ms there
(256.47 -> 164.50) and our encoder-only measurement says 90.6 ms (241.52 -> 150.89) - the vendor's
end-to-end delta is **entirely** the encoder's thread scaling, and the LLM side is untouched.

**Resource picture (the new fact this round).** Sampling `spacemit-tcm-smi` every 50 ms during a
request shows the vision stage holding **4 blocks on the media-worker thread** (cpu8-11), then the
LLM graph's control thread claiming **all 8 blocks**. The two engines **serialise on the 8-block TCM
table**: they do not run concurrently on the AI cores, and the vision stage's blocks are handed back
before the prefill/decode stage takes the table. Thread-budget questions ("LLM 8 + vision 4/8 on 8
cores") are therefore the wrong frame for this deployment; the frame is stage serialisation, and the
lever is the duration of each stage.

## 7. What this changes in the plan

* D1 and D2 are answered; D4 (thread split) is replaced by **stage-duration** work: the encoder is
  35 % of a first-answer budget and its thread scaling is already the vendor's own lever (4 -> 8
  cores saves 90 ms).
* The highest-value open questions are now **D3** (int8 vs fp16 encoder with a numeric gate; 2.17x is
  on the table for the vision path, and the VLM ships fp16), **D6** (per-inference/per-stage fixed
  costs: the first request pays session setup, the second does not, and a robotics loop pays the
  encoder on every *new* frame), and **D7** (what an X100-side pre/post-processing load costs the AI
  stages).
* The operator baselines say where not to look: ViT has no operator hotspot (max 2.0 %), so node-level
  fusion or plugin work on ViT would buy little; the CNN profiles still have a few real targets.
