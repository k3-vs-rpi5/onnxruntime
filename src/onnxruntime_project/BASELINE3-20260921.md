# ONNX Runtime on K3: third round - the int8 vision encoder, and what the provider will not run

Goal of this round: give the VLM path a cheaper vision encoder. `BASELINE-20260921.md` measured the
fp16 encoder at 150.89 ms on 8 AI cores, 35 % of a first-answer budget, and the vendor's own ViT pair
shows int8 at 23.76 ms against fp16 at 48.75 ms (2.17x). A cheaper encoder is therefore the largest
single lever on that budget. Instruments and raw data: `/root/k3-evidence/onnxruntime/
baseline-20260921/` (`int8-encoder-attempt.txt`, `packaged-vs-deb.txt`, `xslim-*.log` on the host).

## 1. What was attempted

| step | tool | result |
|---|---|---|
| dynamic quantisation of the shipped encoder (`--dynq`, no calibration) | xslim 2.1.1 on the fp16 model | builds (127 MB from 253 MB) but the provider refuses it: `Type parameter (T) of Optype (Conv) bound to different types (tensor(float16) and tensor(float))` - xslim's dynq inserts fp32 Q/DQ into an fp16 graph |
| fp16 -> fp32 conversion, then dynq | hand-written onnx pass (cast 457 initializers, retarget I/O, rebuild value_info) | builds, but the provider rejects the graph: a leftover `Cast` (f32->f32) is a node the EP cannot compile (`can not find kernel function for cast, in: f32, out: f32`) |
| clean fp32 copy (every float-typed `Cast` rewired away, shapes re-inferred) | same pass, second iteration | builds and runs on the host ORT CPU EP with the same output as the fp16 original (mean 0.8453) |
| dynq on the clean fp32 copy | xslim 2.1.1 | runs on the provider - and is the measurement below |

Toolchain cost worth recording: xslim 2.1.1 pulls `torch>=2.0`, `torchvision`, `onnxruntime`,
`opencv-python`, `pandas`, `onnx-graphsurgeon` and more (`pip` itself had to be installed on this
host); the CPU-only torch wheel is 196 MB and the whole install took ~20 minutes of wall clock on
this link. The `--dynq` path needs no calibration set; a static path would.

## 2. Result: the dynamic-int8 encoder is three times slower than the shipped fp16 one

`onnxruntime_perf_test` with the vendor's flags, 5 repeats, same model, same session settings:

| encoder | 8 AI cores | 4 AI cores |
|---|---|---|
| shipped fp16 (`fastvlm_vision.f16.onnx`, 253 MB) | **150.49 ms** | 242.42 ms |
| clean fp32 copy (`fastvlm_vision.f32b.onnx`, 505 MB) | 1549.20 ms (**10.3x**) | - |
| fp32 + dynq (`fastvlm_vision.f32b.dynq.onnx`, 128 MB) | 518.59 ms (**3.4x**) | 712.02 ms (2.9x) |

and the provider's `SPACEMIT_EP_DENSE_ACCURACY_LEVEL` knob, which the documentation says governs
"Online MatMul in dynamic quantization models", moves it only within +/-7 %:

| level | 0 (dynq) | 1 (fp16) | 2 (fp32) | 3 |
|---|---|---|---|---|
| dynq model, 8 cores | 469.82 ms | **460.03 ms** | 528.04 ms | 471.60 ms |

None of the four levels approaches the fp16 encoder. The reason is structural: xslim's dynamic
quantisation only rewrites MatMul-type weights, so this encoder's convolutions stay fp32 - and the
provider's fp32 convolution path is the 10x one, not the fp16 one. The provider's fast paths for
this model are its fp16 kernels and (per the vendor's own zoo) *statically* quantised QDQ graphs.

## 3. What this rules in and out

* **Ruled out**: `xslim --dynq` as a cheap int8 encoder. It also produces graphs the provider will
  not load in its first form (mixed fp16/fp32), so the route costs a hand-written conversion pass in
  addition to being slower.
* **Ruled out**: a plain fp32 copy of the encoder. It loads and runs correctly but 10x slower.
* **Ruled in, as the next attempt**: **static quantisation with calibration** - the family the zoo's
  int8 models belong to (`resnet50.q.onnx` 5.47 ms, `vit_b_16.q.onnx` 23.76 ms on the same 8 cores,
  reproduced locally in round 1). That needs a calibration image set and an accuracy evaluation, so
  it is a round of its own; the fp16 encoder stays the deployment choice until it exists.
* A numeric side-note for any future attempt: quantisation error must be judged on **real
  image-like input**. Random noise (what `perf_test -I` feeds) produces outputs in the thousands for
  this model and exaggerates quantisation error to ~300 % relative, which says nothing about
  behaviour on images. The board has `numpy` and the vendor's `spacemit_ort` Python package, so the
  real-input gate can run there directly.

## 4. Also in this round

* **Packaged release vs board deb (the one-time library check).** Same instrument and flags, loader
  verified: resnet50 5.469 vs 5.477 ms, vit_b_16 23.387 vs 23.483 ms (0.15 % and 0.41 %), and 60
  dumped intermediate tensors bit-identical. Either 2.0.6 pair may be used as long as a number says
  which; round 1 used the tarball, the VLM rounds used the deb pair through the board's server.
* **Sustained loop (robotics shape).** YOLOv8n int8, 8 AI cores, three runs of 6,000 inferences
  (~57 s each): 9.478 / 9.478 / 9.490 ms average, P50 9.45 / P90 9.62 / P99 9.82 / P99.9 9.95 ms,
  temperature 31 -> 37 C and then flat. Jitter is not a problem on this stack at this scale, and a
  30 Hz perception loop would use about 29 % of the AI cluster.
* **VLM frame loop.** 30 frames cycling three images: P50 591.7 ms, P90 735.5 ms, max 840.8 ms.
  The media stage runs on **every** frame (`smt_encode_media` 30/30) even when the image is a repeat;
  what the cache saves is the LLM prompt (`prompt_n` 1 after the first round, 21-26 ms against
  184-245 ms). A moving camera therefore pays the encoder per frame, which is exactly the 185-245 ms
  the round-1 budget attributes to it.

## 5. Where the encoder question stands

| option | latency @8 AI cores | status |
|---|---|---|
| shipped fp16 encoder | 150.49 ms | current deployment (vendor, VLM package) |
| dynamic int8 (`xslim --dynq`) | 518.59 ms (best level 460.03) | rejected by measurement |
| plain fp32 | 1549.20 ms | rejected by measurement |
| static int8 QDQ with calibration | - | **not attempted**; the zoo's own int8 CNNs/ViT show the path exists and is fast |

Next step if the encoder stays a priority: a static-Quantization-Aware calibration run (xslim config
with `calibration_parameters`, a few hundred real 512x512 images), then the same three checks -
latency against 150.49 ms, the real-input numeric gate against the fp16 encoder, and the end-to-end
VLM answer on the three test frames.
