# Fourth round: the vendor's model-zoo repositories, measured through our protocol

The two repositories the request named are the vendor's *validation material*, not model dumps:

| repo | HEAD measured | what it is | validation material it ships |
|---|---|---|---|
| `spacemit-com/model-zoo-vision` | `45c3878`, 2026-09-21 | ONNX-Runtime vision deployment library (C++ `VisionService` + Python `spacemit_vision` wheel): detection, classification, segmentation, tracking, face, pose | 38 example families + 5 applications, per-example `download_models.sh`, `test.yaml` (functional + golden + **performance** entries), `tests/scheduled/run_infer_perf.sh` (runs=50, **warmup=5**, optional FPS gate), `scripts/download_all_models.sh`, `scripts/download_assets.sh` |
| `spacemit-com/model-zoo-vlm` | `20a0fa9`, 2026-06-06 | VLM inference service on llama-server with the smt media backend (C++/Python/HTTP gateway, TCM + affinity control) | `docs/testing.md` real-model matrix, `tests/functional/full_model_matrix.py` (single / multi-turn / generate_stream / chat_stream + metrics), `scripts/download_model.sh` for 5 models (766M … 17.6G), model configs under `examples/fastvlm/config/` |

Both were cloned into `.local/model-zoo-{vision,vlm}` and used as-is: their models, their scripts, their
expected behaviours; our protocol (R1-R12 in `METHOD-ALIGNMENT-20260921.md`) supplies the instrument,
the repetitions, the numeric/functional gates and the AI-cluster evidence.

## 1. Vision: their models, our matrix (vendor perf_test, `-r 10`, seed 1, tarball 2.0.6 libs)

| model from their zoo | 1 core | 2 cores | 4 cores | 8 cores | published row |
|---|---|---|---|---|---|
| `yolov8n_no_dfl.q.onnx` (their default detector) | 44.28 | 24.37 | 14.06 | **9.08 ms** | - (sibling `yolov8n.q` = 9.51) |
| `yolo12n.q.onnx` | 110.23 | 59.52 | 33.86 | **22.41 ms** | 21.73 (+3.1 %) |
| `yolo26n.q.onnx` | 60.08 | 34.18 | 20.58 | **14.27 ms** | none published |
| `det_10g_fixed.q.onnx` (SCRFD face, from their `buffalo_l`) | 71.93 | 37.59 | 21.07 | **12.70 ms** | none published |
| `pp_liteseg.q.onnx` (segmentation) | 544.46 | 340.66 | 249.14 | **198.13 ms** | none published |
| `image_encoder.fp16.onnx` (MobileCLIP2-S3, 256²) | - | - | 67.59 | **44.17 ms** | none published |
| `siglip2_vision_encoder_fp16_proj.dynq.onnx` (224²) | - | - | **2104.05** | 2737.58 ms | none published |

Readings:

* The **no-DFL export is 4.5 % faster** than the DFL variant it replaces (9.08 against the published
  9.51 for `yolov8n.q`), which is exactly the trade their README describes: the DFL decode layer moves
  out of the graph into post-processing.
* `yolo12n` reproduces at +3.1 % - at the edge of the +/-3 % band calibrated in round 1, so it is
  flagged rather than accepted.
* **Their own dynq encoder is catastrophically slow**: SigLIP2 vision at 224² takes 2.10 s on 4 AI
  cores and, anomalously, **2.74 s on 8** - slower with more threads. This independently corroborates
  round 3's verdict on `xslim --dynq` (the dynamic route lands on the provider's fp32 path), now on a
  vendor-published dynq artifact rather than one we built.
* Their `examples/rfdetr/scripts/download_models.sh` points at
  `.../vision/rfdetr/rfdetr-nano.fp16.onnx`, which returns **404** today - the script is broken as
  shipped; recorded, not worked around.

## 2. VLM: their matrix script, run on the board

`PYTHONPATH=$PWD/src/python:$PWD python3 tests/functional/full_model_matrix.py --image ... --max-tokens 24
--config fastvlm=examples/fastvlm/config/fastvlm.yaml`, with our TCM/thread sampler alongside:

| their check | result |
|---|---|
| single-turn `generate` | pass (9-char answer) |
| multi-turn `chat` | pass |
| `generate_stream` | pass (18 chunks / 31 chars) |
| `chat_stream` | pass (19 chunks / 32 chars) |
| **their metrics gate (`total_requests >= 4`)** | **FAIL - `total_requests = 2`** |

The failure is theirs, and our metrics probe (`vlm-metrics-probe.py`, using their unmodified
`VlmService`) names it exactly:

| call | `total_requests` after | `last_latency_ms` | `last_ttft_ms` | `last_output_tokens` | `last_tps` |
|---|---|---|---|---|---|
| single-turn | 1 | 2702.2 | 0.0 | -1 | 0.0 |
| multi-turn chat | 2 | 2171.1 | 0.0 | -1 | 0.0 |
| generate_stream | **2** (not counted) | unchanged | 0.0 | -1 | 0.0 |
| chat_stream | **2** (not counted) | unchanged | 0.0 | -1 | 0.0 |

So in this HEAD the two streaming paths do not increment the request counter, and the three
observability fields their README advertises (TTFT, output tokens, tokens/s) are never populated on
this path. The functional validation itself is sound - the answers are correct Chinese descriptions of
the supplied frame - and the run's AI-cluster evidence is clean: thread count grows 20 -> 27 -> **35
during inference**, TCM occupancy goes **4 blocks (vision stage) -> 8 blocks (LLM graph) -> 0** per
request, and `spacemit-tcm-smi` reports 8/8 free afterwards.

Our own latency numbers for the same model (round 1, vendor instrument and llama-server counters) stay
the reference: encoder 241.5 ms at 4 threads / 150.5 ms at 8; first frame 680.7 ms; cached frame
285.4 ms.

## 3. What this round adds to the baseline set

1. Five new vendor-model latency rows (four of them with no published counterpart, so local numbers
   are the reference under R11) plus two VLM-class encoders.
2. An independent, vendor-artifact-level confirmation that **dynq is the slow path** on this stack.
3. A precise defect report for the vendor's VLM harness (streaming metrics), which is the kind of
   finding "use their materials, our protocol" is supposed to produce.
4. Confirmation that their performance harness already uses warmup (5) and a fixed run count (50) -
   the same discipline as our R3/R4 - so their perf numbers and ours are method-compatible.

Still pending when this round closed: the download of their `Qwen3.5-0.8B` VLM package (932 MB, in
flight) to repeat the matrix on a second, larger model; the vision repo's `Qwen`-class encoder pair
(SigLIP2/MobileCLIP2 text towers) would extend the retrieval/VLM matrix.
